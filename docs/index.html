{{ULTIMA_ACTUALIZACION}}

¿Qué es y para qué sirve?

El conector Active Directory/LDAP permite que el agente de Ruvic consulte el directorio corporativo de la empresa — buscar personas, ver a qué grupos pertenecen, o confirmar si una cuenta existe. Funciona tanto con Active Directory (Microsoft) como con LDAP genérico (OpenLDAP, FreeIPA, y otros que sigan el estándar).

Una vez configurado, puedes pedirle al agente cosas como:

  • "Busca a Juan Pérez en el directorio."
  • "¿A qué grupos pertenece el usuario jperez?"
  • "¿Existe la cuenta 'mgomez' en el directorio?"

Operaciones soportadas:

OperaciónQué hace
directory.search_userBusca usuarios por coincidencia parcial en usuario, nombre o correo
directory.get_user_groupsConsulta los grupos de un usuario específico
directory.check_user_existsValida si una cuenta existe (búsqueda exacta)
Conector de solo lectura Este conector no crea, modifica, ni elimina usuarios ni grupos — no tiene ningún método para hacerlo. Los cambios de identidad en un directorio corporativo suelen requerir flujos de aprobación propios (mesa de ayuda, gestión de identidad) que este conector no debe saltarse.

Prerrequisitos

  • Un Active Directory o servidor LDAP accesible por red desde donde corre Ruvic.
  • Un usuario de servicio dedicado con solo permiso de lectura — nunca una cuenta de administrador de dominio.
  • El Base DN (el "punto de partida" de las búsquedas dentro del árbol del directorio).
  • Para pruebas: puedes levantar un servidor OpenLDAP local con Docker en vez de conectarte a un Active Directory productivo (ver sección de Verificación).

Configuración en el fabricante

Si es Active Directory (Microsoft)

  1. Pide al administrador de dominio que cree una cuenta de servicio (ej. svc-ruvic), como cuenta de usuario normal — no como Domain Admin.
  2. Confirma el Base DN de tu dominio — normalmente se ve como DC=miempresa,DC=com. Puedes verlo en "Active Directory Users and Computers" (ADUC), en las propiedades del dominio.
  3. Confirma el DN completo de la cuenta de servicio — algo como CN=svc-ruvic,OU=Service Accounts,DC=miempresa,DC=com. El administrador puede darte este valor exacto desde ADUC (clic derecho en la cuenta → "Copy Distinguished Name", en algunas versiones).
  4. Confirma que LDAPS (puerto 636) esté habilitado en el controlador de dominio — es la vía recomendada. Si no lo está, pide al equipo de infraestructura que lo habilite (requiere un certificado en el controlador de dominio).

Si es LDAP genérico (OpenLDAP, FreeIPA, etc.)

  1. Pide al administrador del directorio un usuario/DN de solo lectura (ej. cn=ruvic-readonly,dc=miempresa,dc=com).
  2. Confirma el Base DN (ej. dc=miempresa,dc=com).
  3. Confirma si el overlay memberOf está habilitado — es necesario para que get_user_groups funcione. La mayoría de instalaciones modernas de OpenLDAP lo tienen activado por defecto.

Permisos requeridos

PermisoPara qué lo usa el conector
Lectura sobre el Base DN configuradoNecesario para las 3 operaciones (búsqueda y consulta de atributos)

No se necesita ningún permiso de escritura — este conector nunca modifica el directorio. En Active Directory, cualquier usuario autenticado normalmente puede leer el directorio por defecto, pero usa igual una cuenta de servicio dedicada para poder auditar y rotar su acceso de forma independiente.

Configuración en Ruvic

Entra a Settings → Conectores, busca la tarjeta Active Directory / LDAP y pulsa Configurar.

Elige el Tipo de directorio correcto (Active Directory o LDAP genérico) — esto determina automáticamente los nombres de atributo internos que usa el conector, no necesitas configurarlos manualmente.

Completa el Servidor, el DN del usuario de servicio y su contraseña, y el Base DN obtenidos en la sección anterior.

Guarda y pulsa Probar conexión.

Verificación

  1. Test de conexión exitoso. El botón Probar conexión debe responder: "Conexión exitosa a [servidor] (active_directory/generic_ldap)".
  2. Prueba mínima con el agente. Pide algo de solo lectura:
    "Busca al usuario [nombre de alguien que sepas que existe] en el directorio."

Para probar sin depender de un Active Directory productivo, puedes levantar un OpenLDAP local con Docker:

docker run -d -p 389:389 -p 636:636 --name openldap-test \
  -e LDAP_ORGANISATION="Empresa Prueba" \
  -e LDAP_DOMAIN="empresa-prueba.com" \
  -e LDAP_ADMIN_PASSWORD="admin123" \
  osixia/openldap

Y configurar el conector con Tipo de directorio "LDAP genérico", Servidor localhost, Puerto 389, SSL desactivado, DN de servicio cn=admin,dc=empresa-prueba,dc=com, y Base DN dc=empresa-prueba,dc=com.

Solución de problemas

Mensaje / síntomaCausa probable y solución
"Bind rechazado..."El DN del usuario de servicio o la contraseña están mal, o la cuenta está bloqueada/deshabilitada. Verifica con el administrador del directorio.
"No se pudo conectar..." (timeout/red)El servidor no es alcanzable desde donde corre Ruvic — puede requerir VPN, whitelist de IP, o el puerto (636/389) está bloqueado por un firewall.
Error de certificado TLS (LDAPS)El certificado del controlador de dominio no es válido/confiable desde donde corre Ruvic. Consulta con el equipo de infraestructura sobre la cadena de certificados.
search_user no encuentra a alguien que sabes que existeRevisa que el Base DN configurado incluya la OU donde está esa persona — si acotaste el Base DN a una sola OU, usuarios en otras OU no aparecerán.
get_user_groups retorna una lista vacía para alguien que sí tiene gruposEn LDAP genérico, confirma que el overlay memberOf esté habilitado en el servidor — sin él, esta operación no tiene de dónde leer los grupos.

Preguntas frecuentes y notas de seguridad

¿El agente puede modificar el directorio?

No. Este conector no tiene ningún método de escritura — es de solo lectura por diseño.

¿Qué pasa si el usuario de servicio tiene más permisos de los necesarios?

El conector solo va a usar operaciones de lectura, pero si la cuenta configurada tiene permisos de escritura o administrativos, ese riesgo existe fuera del conector (por ejemplo, si alguien más usa esas mismas credenciales). Por eso se recomienda una cuenta dedicada y acotada solo a lectura.

¿Dónde queda guardada la contraseña del usuario de servicio?

Como secreto en el almacén de credenciales de la plataforma. La interfaz nunca vuelve a mostrarla.

Rotación de credenciales

Sigue la política de contraseñas del dominio para el usuario de servicio, y actualiza el valor en el formulario del conector cuando la rotes.

Buenas prácticas Usa siempre una cuenta de servicio dedicada, nunca una cuenta de administrador de dominio; acota el Base DN a la OU específica que el agente necesita; usa LDAPS (cifrado) en vez de LDAP plano; y confirma periódicamente con el equipo de identidad que la cuenta de servicio sigue teniendo únicamente permisos de lectura.
